1. SSL handshake errors do not show in request explorer by default.

We have bug 2748 open for this and there is a workaround. If you add this to a frontend or the defaults section your frontends are using, that will send TLS handshake errors in a format that can be captured in Request Explorer:

error-log-format "%ci:%cp [%t] %ft -/- %Th/%Tw/%Tc/%Tt/%Tu -1 %B \"\" \"\" %ts-- %ac/%fc/%bc/%sc/%rc %sq/%bq {} {} \"TLS /TLS_HANDSHAKE_FAILURE/%{-Q}[ssl_c_ca_err_depth]/ HTTP/1.1\" %[fc_err]/%[ssl_fc_err,hex]/%[ssl_c_err]/%[ssl_c_ca_err]/%[ssl_fc_is_resumed] %[ssl_fc_sni]/%sslv/%sslc"

2. Could this indicate that the issue is occurring at the TCP layer?

Yes. That is very possible. We can't see any handshake failures from that IP in the pcap. It would be more helpful if the Java app could log the TCP source port in use at the time of the failure, then we could filter down the pcap for that port. But since we cannot see it, maybe the failure happens before HAProxy is involved? My recommendation is to log the tcp source port in Java then perform a longer capture to try and collect the failure. You might add more captures, like on the server and haproxy at the same time, just to rule out any packet drops or intermediate modifications.
